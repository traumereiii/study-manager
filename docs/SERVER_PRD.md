# 차곡 서버 PRD

> 작성일: 2026-10-16 · 상태: 구현 기준 v0.2  
> 확정 조건: **Kotlin + Spring, JDK 25, Gradle 9.8.1, MySQL 8, JPA, JWT 인증**  
> 기준 구현: `frontend/`의 Vue 3 화면, 도메인 타입, `StudyApi`, 모킹 API

## 1. 목적과 배경

차곡은 문제집에 학습 카드를 등록하고, 정답을 확인한 뒤 `알아요 / 몰라요`로 기억 상태를 평가하는 개인 학습 서비스다. 서버는 현재 브라우저 메모리와 `localStorage`에 저장하는 데이터를 영구 저장하고, 문제집·문제·평가 이력·설정의 일관성을 보장한다.

기존 [제품 PRD](PRD.md)는 `prototype/` 구현을 설명한다. 현재 `frontend/`에는 문제집 보관·휴지통·완전 삭제, Markdown·이미지 첨부, 카드별 학습 시간 통계가 추가돼 있다. 서버 범위는 이 최신 프런트엔드 구현을 우선한다. 이 문서는 서버 요구사항을 정의하며 서버 구현 완료를 의미하지 않는다.

### 1.1 목표

- 기존 화면의 기능을 실제 HTTP API와 DB로 제공한다.
- 서버 재시작과 브라우저 새로고침 후에도 저장된 학습 데이터를 유지한다.
- 평가 중복 요청으로 이력과 암기 레벨이 중복 변경되는 것을 방지한다.
- 문제 삭제와 레벨 초기화 후에도 보존해야 하는 학습 통계를 유지한다.
- 프런트엔드의 `StudyApi` 교체 지점을 활용해 연동 변경을 최소화한다.

## 3. 사용자 흐름과 책임

1. 앱 실행 시 서버에서 문제집·카드·평가 이력·설정을 불러온다.
2. 문제집과 문제를 만들거나 수정하면 서버 저장 성공 후 화면에 반영한다.
3. 학습 시작 시 해당 문제집의 카드 순서를 클라이언트가 고정한다.
4. 사용자가 정답을 확인한 뒤 평가하면 서버가 레벨·평가 이력·최근 학습일을 함께 저장한다.
5. 모든 카드의 평가 저장이 끝나면 당일 학습 완료를 저장한다.
6. 통계 화면은 서버에 저장된 이력을 기준으로 횟수·비율·시간을 표시한다.

| 서버 책임 | 클라이언트 책임 |
| --- | --- |
| 입력 검증, 리소스 관계 확인, 저장과 조회 | 화면 이동, 폼 상태, 접근성 |
| 평가별 레벨 변경과 이력 원자적 저장 | 정답 공개, 보기 선택, 학습 순서·진행 위치 |
| 기준 날짜·평가 시각 부여 | 제한시간과 실제 학습 시간 측정 |
| 설정·알림 표시 날짜 저장 | 단축키 실행, 앱 내 알림 표시·중복 억제 |
| 저장 실패·중복 요청 처리 | 실패 안내, 입력 보존, 재시도와 버튼 중복 클릭 방지 |

정답도 카드 조회 응답에 포함한다. 정답 공개는 학습 편의를 위한 화면 상태이며, 시험 보안이나 부정행위 방지 기능으로 정의하지 않는다.

## 4. 기능 요구사항

### 4.1 문제집 관리

- 이름·한 줄 소개·아이콘·분류를 저장한다. 이름 중복은 허용한다.
- 이름은 앞뒤 공백 제거 후 1~60자, 소개는 공백 제거 후 최대 160자다.
- 분류는 `단어 / 용어 / 개념 / 미지정`만 허용한다. 아이콘은 프런트엔드의 `BOOK_ICONS` 목록을 따른다.
- 신규 문제집은 카드 0개, 최근 학습일·완료일 없음으로 생성한다. 색상 기본값은 기존 `DEFAULT_BOOK_COLOR`를 따른다.
- 제목·소개·아이콘·분류 변경은 카드·레벨·이력·완료일을 변경하지 않는다.
- `archived`, `deleted`를 별도로 저장한다. 휴지통 여부가 목록 분류보다 우선한다.
- 휴지통 이동은 기존 보관 상태를 유지하고, 복원은 `deleted=false`만 적용한다. 보관 상태였던 문제집은 보관함으로 복원한다.
- 보관·휴지통 상태에서는 학습 평가와 카드 변경을 거부한다. 상태 복원과 문제집 메타데이터 수정은 허용한다.
- 완전 삭제는 휴지통의 문제집에만 허용하며 문제집·카드·첨부 이미지·평가 이력을 함께 제거한다. 관련 멱등 응답 데이터도 제거한다.
- 휴지통 이동에는 데이터 보존 기간이나 자동 삭제를 적용하지 않는다.

### 4.2 문제 관리

| 필드 | 서버 검증 |
| --- | --- |
| 유형 | `qa`, `blank`, `choice` |
| 질문 | 공백 제거 후 1~20,000자 |
| 정답 | `qa`·`blank`에서 공백 제거 후 1~20,000자 |
| 해설 | 선택, 공백 제거 후 최대 20,000자 |
| 빈칸 | `blank` 질문에 연속 밑줄 두 개 이상(`__`) 포함 |
| 선다형 보기 | 정확히 4개, 각각 공백 제거 후 1~5,000자, 중복 불가 |
| 선다형 정답 | 정수 인덱스 0~3, 해당 보기로 `answer`를 서버에서 생성 |
| 초기 레벨 | 서버가 Level 1 부여 |

문자 길이는 현재 JavaScript 구현과 맞춰 UTF-16 코드 단위로 계산한다. 질문·정답·해설·보기는 Markdown 원문을 저장한다.

- 유형 변경을 지원한다. 선다형에서 다른 유형으로 변경하면 이전 `options`, `correct`를 제거한다.
- 수정 시 카드 ID·레벨·기존 이력을 유지한다.
- 카드 생성·수정·레벨 초기화 성공 시 문제집의 당일 완료 상태를 해제한다.
- 카드 삭제는 해당 카드를 제거하되 기존 평가 이력을 유지한다. 현재 모킹 동작처럼 삭제 자체는 완료 상태를 해제하지 않는다.
- 레벨 초기화는 해당 카드만 1로 변경하고 이력을 추가·삭제하지 않는다. 이미 1이면 같은 결과를 반환한다.
- 카드의 문제집 소속을 검증한다. 요청한 `bookId`와 카드의 실제 소속이 다르면 평가를 거부한다.
- 클라이언트가 `level`, 학습일, 다른 카드의 ID 등을 생성·수정 입력에 끼워 넣어 서버 상태를 바꾸지 못하게 한다.

### 4.3 Markdown과 이미지

기존 `assets: Record<string, string>`과 `asset:img-...` 참조를 P0에서 유지한다. 카드 저장 요청으로 Data URL 이미지를 받고, DB에는 카드와 연결된 이미지 바이트·MIME·크기를 별도로 저장한다. 조회 시 기존 계약의 Data URL 맵으로 반환한다.

- 사용자 이미지는 PNG·JPEG·WebP, 파일별 디코딩 크기 최대 2 MiB로 제한한다.
- MIME 문자열뿐 아니라 실제 파일 형식과 이미지 디코딩 가능 여부를 검증한다. 사용자 SVG·HTML 파일은 허용하지 않는다.
- 카드당 최대 5개, 디코딩 합계 최대 10 MiB를 제안한다. 이 추가 제한은 프런트엔드에도 반영한다.
- 카드 생성·수정 요청 본문 한도는 Base64 증가분을 고려해 16 MiB로 제안하고, 앱과 프록시에 동일하게 적용한다.
- 질문·정답·해설·보기에서 참조하는 자산만 저장한다. 누락된 참조는 검증 오류로 처리한다.
- 카드 저장은 본문과 이미지까지 함께 성공하거나 모두 취소돼야 한다. 수정 시 더 이상 참조하지 않는 이미지는 제거한다.
- 서버가 Markdown의 외부 URL을 대신 요청하거나 파일 경로로 해석하지 않는다.
- 현재 예시의 내장 SVG는 운영 DB에 기본 주입하지 않는다. 개발 예시를 넣을 경우 서버가 관리하는 PNG 등으로 변환한다.
- HTML 출력 시 기존 프런트엔드의 Markdown 정화 처리를 유지한다.

이미지 별도 업로드·다운로드 API와 객체 저장소는 P1이다. 이때 `assets`의 값이 URL로 바뀌므로 현재 Data URL만 허용하는 렌더러도 함께 수정해야 한다.

### 4.4 학습 평가와 완료

- `known=true`는 레벨 +1, `known=false`는 -1이며 1~5로 제한한다. 상·하한에서도 평가 이력은 남긴다.
- 평가는 자기 평가다. 선택한 보기의 정오답으로 결과를 덮어쓰지 않는다.
- 평가 1건은 카드 레벨 변경·평가 이력 생성·문제집 최근 학습일 변경을 한 트랜잭션으로 처리한다.
- 평가 시각 `at`는 서버 UTC 시각, `date`와 최근 학습일은 그 시각을 `Asia/Seoul`로 변환한 날짜로 기록한다.
- `durationMs`는 0 이상의 정수, `revealMs`는 `null` 또는 `0 <= revealMs <= durationMs`인 정수다. 두 값의 최대치는 86,400,000ms로 제안한다.
- 시간은 클라이언트 측정값이며 편집·다른 화면·백그라운드 시간을 제외한다. 서버는 이를 실제 시청 시간으로 인증하지 않는다.
- 정답 공개와 제한시간 만료만으로 평가를 생성하지 않는다. 제한시간 만료는 자동 `몰라요`나 다음 문제 이동을 발생시키지 않는다.
- 같은 평가를 네트워크 오류로 재전송해도 한 번만 반영한다. 별도 학습에서 같은 카드를 다시 평가하면 새 이력을 생성한다.
- 평가 응답은 현재 계약의 `{ card, entry, book }`을 제공한다.
- 서버 저장 실패 시 화면은 현재 문제에 남고 동일 요청 키로 재시도한다. 메모리에서만 성공 처리하고 다음으로 넘어가지 않는다.

오늘 학습 예정 수는 다음과 같다. 부분 진행에 따라 남은 카드 수를 차감하거나 카드별 복습일을 계산하지 않는다.

```text
보관 또는 휴지통 상태이면 0
완료일이 오늘이면 0
그 외에는 현재 전체 카드 수
```

완료일은 완료 요청을 서버가 처리한 날짜다. 모든 카드 평가 저장 후 `completeBook`을 호출하며, 완료 저장 실패는 평가를 다시 제출하지 않고 완료 요청만 재시도한다. 빈 문제집은 완료할 수 없다. 완료 후에도 전체 카드를 다시 학습할 수 있다.

P0에서는 완료 여부를 기존 클라이언트가 선언한다. 서버가 모든 카드의 평가 완료를 검증하거나 여러 기기의 세션을 병합하는 기능은 제외한다. 평가 후 카드 구성 변경으로 오래된 완료 요청이 들어오는 충돌까지 보장하려면 세션·리비전 계약이 추가로 필요하다.

### 4.5 통계

- 전체 요약: 오늘 평가 횟수, 누적 평가 횟수, `알아요` 비율, 평가가 있는 서로 다른 날짜 수.
- 최근 7일: 오늘을 포함해 날짜순 7개 날짜를 표시하고 기록 없는 날은 0회로 채운다.
- 문제집별: 현재 카드 수·평균 레벨, 평가 횟수, `알아요` 비율.
- 카드별: 평가 횟수, 알아요·몰라요 횟수, 비율, 누적·평균 학습 시간, 마지막 학습, 평가 이력.
- 같은 카드 반복 평가는 매번 횟수에 포함한다. 비율은 `알아요 횟수 / 평가 횟수 × 100`을 반올림한 정수다.
- 전체 이력이 없으면 요약 비율은 0%, 개별 문제집·카드의 이력이 없으면 비율은 `null`이다. 카드가 없는 문제집의 평균 레벨 표시는 `—`다.
- 카드 삭제 후에도 전체·문제집 통계에 기존 평가를 포함한다. 삭제된 카드의 상세 화면은 제공하지 않는다.
- 보관·휴지통 문제집의 이력은 전체 요약에 포함한다. 문제집별 표에는 휴지통 문제집을 제외한다. 완전 삭제 시 해당 이력은 모든 통계에서 제외한다.
- 과거 날짜·결과·시간·평가 후 레벨은 카드 수정이나 레벨 초기화로 바꾸지 않는다.

P0 통계 계산은 기존 프런트엔드 스토어를 재사용한다. 서버 집계와 이력 페이지 조회는 P1에서 함께 전환한다.

### 4.6 설정과 알림

- 기본값은 단축키 켬, 정답 공개 `Space`, 몰라요 `1`, 알아요 `2`, 알림 끔, 알림 시각 `20:00`, 제한시간 0초다.
- 단축키는 기존 `KEY_OPTIONS` 목록에서 서로 다른 세 개를 선택한다.
- 알림 시각은 유효한 24시간제 `HH:mm`, 제한시간은 0~600 사이 정수다. 0은 무제한이다.
- 설정 저장 실패 시 기존 서버 설정을 유지하고, 클라이언트는 작성 중인 입력을 보존한다.
- 마지막 알림 날짜는 `YYYY-MM-DD` 또는 초기값 빈 문자열로 제공한다. 동일 날짜 기록은 중복 생성하지 않고 과거 날짜로 되돌리지 않는다.
- 서버는 알림 설정과 날짜를 저장한다. 앱이 열려 있을 때의 배너 표시와 시각 확인은 프런트엔드가 담당한다.
- 기기 간 알림을 정확히 한 번만 표시하는 보장은 이번 범위에서 제외한다.

## 5. API 요구사항

### 5.1 공통 계약

- 기본 경로는 `/api/v1`, 요청·응답은 UTF-8 JSON이다.
- 외부 ID는 문자열로 제공하고 서버가 생성한다. 신규 ID는 UUID 기반으로 하며 클라이언트는 접두사 등 내부 형식에 의존하지 않는다.
- 필드 이름과 응답 구조는 `frontend/src/types/index.ts`, `frontend/src/api/types.ts`를 우선한다. DB 엔티티를 직접 노출하지 않는다.
- 생성은 201, 조회·수정은 200, 응답 본문 없는 삭제·기록 갱신은 204를 사용한다.
- 리소스 없음 404, 잘못된 입력·관계 400, 인증 실패 401, 권한 없음 403, 상태 충돌·멱등 키 충돌 409, 본문 초과 413, 서버 오류 500으로 구분한다.
- 서버 오류의 내부 예외·SQL·파일 경로는 응답에 노출하지 않는다.

### 5.2 P0 엔드포인트

| 메서드 | 경로 | 기존 메서드 / 응답 |
| --- | --- | --- |
| POST | `/auth/login` | admin / admin1234 검증 → 토큰 쌍 |
| POST | `/auth/refresh` | RefreshToken 검증·회전 → 토큰 쌍 |
| POST | `/auth/logout` | 해당 로그인 세션의 토큰 폐기 → 본문 없음 |
| GET | `/auth/me` | 현재 관리자 조회 |
| GET | `/bootstrap` | `bootstrap` → `{ books, cards, history, settings, alarmLastDate }` |
| POST | `/books` | `createBook` → `Book` |
| PUT | `/books/{bookId}` | `updateBook` → `Book` |
| PATCH | `/books/{bookId}/state` | `setBookState` → `Book` |
| DELETE | `/books/{bookId}` | `purgeBook` → 본문 없음, 휴지통에서만 가능 |
| POST | `/books/{bookId}/cards` | `createCard` → `{ card, book }` |
| PUT | `/cards/{cardId}` | `updateCard` → `{ card, book }` |
| DELETE | `/cards/{cardId}` | `deleteCard` → 본문 없음 |
| POST | `/cards/{cardId}/level-reset` | `resetCardLevel` → `{ card, book }` |
| POST | `/evaluations` | `submitEvaluation` → `{ card, entry, book }` |
| POST | `/books/{bookId}/completion` | `completeBook` → `Book` |
| PUT | `/settings` | `saveSettings` → `Settings` |
| PUT | `/settings/alarm-last-date` | `setAlarmLastDate` → 본문 없음 |

상태 변경 본문은 `{ "archived": true }` 또는 `{ "deleted": true }` 등 지정한 필드만 변경한다. 알림 날짜 본문은 `{ "date": "2026-10-16" }`이다. 다른 입력은 기존 `BookInput`, `CardInput`, `Settings`를 따른다.

`bootstrap`은 휴지통을 포함한 문제집·카드와 보존된 이력을 반환한다. 응답 내 컬렉션은 일관된 DB 스냅샷에서 읽고, 문제집·카드는 생성 순서와 ID, 이력은 시각과 ID로 안정적으로 정렬한다. 데이터가 없는 서버는 빈 목록과 기본 설정을 반환하며 운영 환경에 예시 데이터를 자동 생성하지 않는다.

로그인·재발급과 상태 확인을 제외한 API는 `Authorization: Bearer <accessToken>` 헤더를 요구한다. 로그인과 재발급 요청·응답의 상세 예시는 [서버 실행 문서](../backend/README.md)를 따른다.

### 5.3 평가 멱등성

```http
POST /api/v1/evaluations
Idempotency-Key: <평가 동작별 UUID>
Content-Type: application/json

{
  "bookId": "...",
  "cardId": "...",
  "known": true,
  "durationMs": 12000,
  "revealMs": 8000
}
```

- 키는 필수이며 클라이언트가 평가 동작 시작 시 생성하고 성공 여부가 확인될 때까지 유지한다.
- 같은 키·같은 본문이면 최초 성공 응답을 반환하며 레벨과 이력을 다시 변경하지 않는다. 재시도 이후 카드가 바뀌었더라도 최초 응답을 재현한다.
- 같은 키·다른 본문이면 409를 반환한다. 동시 중복 요청도 DB 유일성 제약으로 차단한다.
- 성공 결과와 요청 본문 해시를 평가 트랜잭션에 함께 저장한다. 저장 실패로 롤백되면 키도 성공 처리하지 않는다.
- 멱등 기록은 평가 이력과 함께 유지하고 문제집 완전 삭제 시 함께 제거한다.

생성·평가 요청을 통신 라이브러리가 무조건 자동 재시도하지 않는다. 카드·문제집 생성의 멱등성은 P0 필수가 아니므로 응답 유실 시 재조회하고 사용자가 재시도하도록 안내한다.

### 5.4 오류 응답 예시

```json
{
  "code": "VALIDATION_ERROR",
  "message": "문제 내용을 1~20,000자로 입력해 주세요.",
  "fieldErrors": [{ "field": "question", "message": "필수 항목입니다." }],
  "traceId": "..."
}
```

대표 코드는 `VALIDATION_ERROR`, `BOOK_NOT_FOUND`, `CARD_NOT_FOUND`, `BOOK_NOT_ACTIVE`, `BOOK_NOT_DELETED`, `IDEMPOTENCY_CONFLICT`, `PAYLOAD_TOO_LARGE`, `INTERNAL_ERROR`다. 프런트엔드는 HTTP 상태와 코드로 처리하고 `message`를 사용자에게 표시한다.

### 5.5 P1 조회 계약

전체 로딩의 데이터량이 커지면 다음 API를 도입하고, `bootstrap`과 스토어를 부분 로딩 구조로 함께 변경한다. 기존 메서드 교체만으로 대규모 데이터 처리가 해결된다고 가정하지 않는다.

- 문제집 목록·상세·요약 조회.
- `GET /books/{bookId}/cards?q=&level=&page=`: 질문·정답·해설·보기의 대소문자 무시 부분 검색, 최대 200자, 레벨과 함께 필터링.
- 페이지는 1부터, 기본 10개, 저장 순서로 조회한다. 초과 페이지는 마지막 유효 페이지로 보정하고 빈 결과는 1페이지·총 0건으로 반환한다.
- 전체·최근 7일·문제집별 집계 조회와 카드별 이력 페이지 조회.
- 이미지 본문은 목록에서 분리하고 필요한 카드에서만 로딩한다.

## 6. 데이터 요구사항

다음은 논리 모델 초안이며 구체적인 DDL은 서버 구현 단계에서 확정한다.

| 모델 | 주요 데이터 | 수명·관계 |
| --- | --- | --- |
| Book | ID, 이름·소개·아이콘·분류·색상, 보관·휴지통, 최근 학습일·완료일, 생성·수정 시각 | 카드의 부모 |
| Card | ID, 문제집 ID, 유형, 질문·정답·해설, 레벨, 생성 순서·시각 | 문제집에 소속 |
| CardOption | 카드 ID, 인덱스 0~3, 내용, 정답 여부 | 선다형 카드에 소속 |
| CardAsset | 카드 ID, 자산 ID, MIME, 크기, 이미지 바이트 | 카드와 함께 저장·삭제 |
| Evaluation | ID, 문제집 ID, 카드 참조, 원래 카드 ID, 날짜·시각, 결과, 시간, 평가 후 레벨 | 수정하지 않는 평가 이력 |
| IdempotencyRecord | 키, 요청 해시, 최초 응답, 평가·문제집 ID | 평가와 함께 생성·삭제 |
| Settings | 고정 설정 ID, 단축키, 알림, 제한시간, 마지막 알림 날짜 | 개인 서버에 1개 |
| RefreshSession | ID, RefreshToken 해시, 최초 만료 시각, 폐기 여부, 생성 시각 | 로그인마다 생성, 재발급 시 해시 교체 |

- 카드 삭제 시 평가의 카드 FK는 `SET NULL`로 처리하고 원래 카드 ID 문자열을 보존한다. API의 `HistoryEntry.cardId`는 원래 ID를 반환해 기존 계약을 유지한다.
- 문제집 완전 삭제는 소속 평가까지 제거한다. 휴지통 이동은 삭제 전파를 실행하지 않는다.
- 레벨 1~5, 음수 시간 금지, 카드별 보기 인덱스·자산 ID 중복 금지, 멱등 키 유일성을 DB에서도 보장한다.
- 초기 인덱스 후보는 카드의 `(book_id, created_at, id)`, 평가의 `(book_id, at, id)`, `(original_card_id, at, id)`, `(date)`다.
- 평가·카드 변경·문제집 완전 삭제가 경합할 때 동일 문제집을 먼저 잠그는 일관된 순서로 처리하고, 커밋된 레벨을 기준으로 평가한다.
- 서로 다른 평가 두 건은 모두 반영한다. 예를 들어 Level 1에서 `알아요` 두 건이 동시에 성공하면 이력 2건·최종 Level 3이다.
- 폼의 동시 편집은 마지막 성공 저장을 적용한다. 오래된 폼 덮어쓰기 방지를 위한 버전 충돌 검출은 후속 범위다.

공식 문서 확인 결과 Spring Boot 4.1.1은 Java 25를 지원 범위에 포함하며, Gradle은 9.1.0부터 Java 25에서 실행할 수 있다. Kotlin은 2.3.0부터 JVM 25 바이트코드를 생성한다. 따라서 JDK만 25로 설치하고 Kotlin JVM target을 낮은 기본값으로 두지 않도록 Java·Kotlin toolchain과 컴파일 target을 모두 25로 일치시킨다. [Spring Boot 시스템 요구사항](https://docs.spring.io/spring-boot/system-requirements.html), [Gradle Java 호환성](https://docs.gradle.org/current/userguide/compatibility.html), [Kotlin 2.3 JVM 25 지원](https://kotlinlang.org/docs/whatsnew23.html)

`backend/` 단일 애플리케이션에 `auth`, `study`, `common` 패키지를 두고 Controller·Service·Repository·DTO를 분리한다. 트랜잭션은 서비스에서 관리한다. Spring 프록시·JPA 엔티티에 필요한 Kotlin 플러그인을 적용한다. Redis·메시지 브로커·마이크로서비스는 초기 요구사항에 포함하지 않는다.

## 8. 품질과 운영 요구사항

### 8.1 정합성과 장애 대응

- 모든 변경은 DB 커밋 후 성공 응답을 반환한다. DB 오류를 빈 데이터나 저장 성공으로 위장하지 않는다.
- 평가 또는 이미지 저장의 일부만 반영되는 상태를 허용하지 않는다.
- 서버·DB 재시작 후 저장 데이터가 복원돼야 한다.
- 운영 스키마는 Flyway로 관리하고 자동 스키마 갱신을 사용하지 않는다.
- 날짜 계산에는 주입 가능한 서버 시계를 사용하고 자정 경계를 테스트한다. 클라이언트의 오늘·최근 7일·알림 날짜도 동일 시간대로 맞춘다.
- 개인 운영 기준 일 1회 백업, RPO 24시간·RTO 4시간을 목표로 제안한다. DB와 이미지가 함께 복원되는 절차를 문서화하고 검증한다.

### 8.2 접근과 데이터 취급

- 관리자 계정은 `admin / admin1234`로 고정하고 비밀번호는 BCrypt로 비교한다. 회원가입은 제공하지 않는다.
- JWT는 HS256으로 서명하며 서명·issuer·subject·발급 시각·만료 시각·종류를 검증한다. 서명 키는 환경변수로 받고 최소 32바이트로 제한한다.
- AccessToken은 발급 시점부터 2시간, RefreshToken은 최초 로그인 시점의 UTC 달력상 1개월이다. 재발급 시 최초 RefreshToken 만료일은 연장하지 않는다.
- RefreshToken은 DB에 SHA-256 해시만 저장하고 재발급 시 교체한다. 동일 RefreshToken의 동시 재발급은 한 번만 성공한다.
- 로그아웃 시 로그인 세션을 폐기하고 그 세션의 AccessToken과 RefreshToken 모두 거부한다. 다른 로그인은 유지한다.
- 인증은 Authorization Bearer 헤더만 사용하며 브라우저 쿠키와 HTTP 세션은 사용하지 않는다.
- CORS는 개발·운영 프런트엔드 출처를 명시한다. CORS를 접근 제어의 대체 수단으로 간주하지 않는다.
- DB 접속 정보는 환경변수로 받고 저장소에 넣지 않는다.
- 로그에는 문제 원문·정답·이미지 Base64·DB 자격 증명을 남기지 않는다. 요청 추적 ID, 경로, 상태, 처리 시간, 오류 코드를 기록한다.
- 외부에서 제공할 경우 HTTPS를 사용하고 관리용 엔드포인트의 노출을 제한한다.

### 8.3 성능과 크기 한계

- 초기 검증 데이터셋은 문제집 20개·카드 500개·평가 10,000건·첨부 이미지 원본 총 10 MiB로 제안한다.
- 기준 장비 2 vCPU·4 GiB, 동시 요청 5개에서 텍스트 변경·평가 API의 서버 처리 시간 p95 300ms 이하를 목표로 한다. 이미지 요청과 최초 로딩은 별도 측정한다.
- 같은 데이터셋에서 `bootstrap` DB 조회·직렬화 p95 2초 이하를 목표로 하고, 실제 네트워크 다운로드·브라우저 파싱 시간은 별도로 기록한다.
- 전체 로딩 P0는 소규모 개인용에 한정한다. 이력·이미지가 계속 증가하면 전송량과 브라우저 메모리가 병목이 되므로 P1 부분 로딩을 우선한다.
- 성능 수치는 검증 목표이며 현재 측정 결과가 아니다. 운영 데이터 초과 시 기록을 잘라서 정상 로딩으로 표시하지 않는다.

## 9. 프런트엔드 연동과 기존 데이터

1. `frontend/src/api/`에 `StudyApi`를 구현하는 HTTP 어댑터를 추가한다.
2. 기존 `setApi` 교체 지점을 사용하고 개발용 모킹 API 선택 기능을 유지한다.
3. 평가 요청 키 유지·실패 시 현재 문제 보존·완료 요청 별도 재시도를 반영한다.
4. 이미지 수·총량 검증과 서버 오류 표시를 추가하고 날짜 계산을 서버 기준과 맞춘다.
5. 재조회 시 중복 이력이 추가되지 않게 서버 ID로 병합한다. 문제집 완전 삭제 시 클라이언트의 해당 이력도 제거한다.
6. 초기 데이터 로딩 실패는 오류와 재시도를 제공하고 자동으로 예시 데이터로 전환하지 않는다.

현재 모킹 API보다 엄격해지는 소속 검증·비활성 문제집 변경 금지·실패 처리 때문에 어댑터만 교체하면 모든 동작이 완성되지는 않는다. 필요한 화면·스토어 수정은 위 항목으로 한정한다.

기존 브라우저 데이터는 `prototype`의 `chagok-study-preview-v1`과 Vue의 `chagok-vue-mock-v1` 두 형식이 있다. P0는 새 서버 저장소로 시작하며 기존 키를 자동 업로드하거나 삭제하지 않는다. 기존 데이터를 유지해야 하면 가져오기를 출시 필수 범위로 올리고 ID 매핑·중복 방지·이미지 변환·결과 미리보기 요구사항을 별도 정의한다.

## 10. 검증과 완료 기준

| 영역 | 수용 기준 |
| --- | --- |
| 실행 환경 | JDK 25에서 Wrapper 빌드·테스트·패키지 실행 성공, Java·Kotlin target 일치 |
| 빈 서버 | 예시 데이터 없이 빈 목록·기본 설정 반환, 빈 문제집 학습·완료 거부 |
| 문제집 | 생성·수정·보관·휴지통·원래 보관 상태 복원·완전 삭제가 재조회 후 유지 |
| 입력 검증 | 글자 수 경계, 잘못된 유형·빈칸·중복 보기·정답 인덱스·소속 오류 거부 |
| 이미지 | 허용 형식·2 MiB 경계·개수·총량 검사, 참조 누락 거부, 저장 실패 전체 롤백 |
| 평가 | 레벨 1·5 경계에서도 이력 기록, 카드·이력·최근 학습일 동시 반영 |
| 중복·경합 | 동일 키 동시·재시도는 이력 1건, 다른 본문은 409, 다른 키 평가는 모두 반영 |
| 장애 | 평가 중 DB 실패 시 레벨·이력 모두 롤백, 응답 유실 재시도 시 최초 결과 반환 |
| 완료 | 마지막 평가 후 완료 저장, 완료 실패 시 완료만 재시도, 반복 학습 가능 |
| 수정·삭제 | 카드 수정·레벨 초기화 후 이전 이력 유지, 카드 삭제 후 통계 유지 |
| 통계 | 반복 평가·0건·삭제 카드·휴지통·완전 삭제·시간 합계와 평균 규칙 일치 |
| 날짜 | 서울 자정 전후 평가의 날짜·최근 7일·오늘 예정 수가 같은 기준으로 동작 |
| 연동 | 모킹 API를 HTTP로 교체해 생성 → 학습 → 평가 → 통계 → 재접속 흐름 완료 |
| 인증 | 계정 검증·2시간/1개월 만료·재발급 회전·동시 재발급·로그아웃 폐기 검증 |
| 운영 | MySQL 8 마이그레이션·재시작 영속성·백업 복원 검증, 추적 가능한 오류 로그 |

도메인 규칙 테스트와 실제 MySQL 8 통합 테스트를 사용한다. 평가 멱등성·삭제 이력 보존·트랜잭션 롤백은 모킹 저장소 테스트만으로 완료 처리하지 않는다. 프런트엔드 타입 검사·기존 테스트·주요 브라우저 흐름도 연동 변경 후 검증한다.

## 11. 구현 순서

1. **서버 기반**: JDK 25·Kotlin·Boot·Gradle 9.8.1 고정, MySQL 8·JPA·Flyway·JWT 인증·예외 응답·실행 문서.
2. **콘텐츠 저장**: 문제집 상태 전환, 카드 유형별 검증과 이미지, bootstrap.
3. **학습 기록**: 평가 트랜잭션·멱등성·레벨 초기화·완료·설정 저장.
4. **화면 연동**: HTTP 어댑터, 평가 실패·완료 재시도, 날짜·이미지 제한, 이력 동기화.
5. **완료 검증**: 동시 요청·DB 장애·삭제·통계·성능·백업 복원 확인.

일정과 공수는 담당자·배포 환경·인증 및 데이터 이전 범위를 결정한 뒤 산정한다.
